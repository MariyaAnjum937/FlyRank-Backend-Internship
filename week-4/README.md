

# FlyRank Backend Internship — Week 4

# Auth Login & Protect

A secure authentication API built using **Node.js, Express.js, and Supabase Auth**.

This project was first implemented manually, stage by stage, to understand authentication, JWT access tokens, token verification, middleware protection, logout, and API documentation.

As the optional Stage 7 bonus, the same setup was also generated by an AI assistant in a separate `aiWorker` folder and tested against the required authentication checkpoints.

---

## 🎯 Goal

The goal of this project is to build a secure API that supports:

- User Sign Up
- User Log In
- User Log Out
- JWT access token authentication
- Protected API routes
- Token verification using Supabase
- Reusable authentication middleware
- Swagger UI API documentation
- GitHub publication

Supabase Auth is used as the Identity Provider to manage users and issue JWT access tokens.

## 🔐 Authentication Flow

The application follows this flow:

```text
Client
   ↓
Sign Up / Log In
   ↓
Supabase Auth
   ↓
JWT Access Token
   ↓
Client sends token in Authorization Header
   ↓
Express Middleware
   ↓
Supabase verifies token
   ↓
Protected Route
   ↓
Response
```

Protected requests use:

```http
Authorization: Bearer <access_token>
```

# 🧑‍💻 Stage 1 — Sign Up & Log In

Implemented:

### `POST /auth/signup`

Accepts:

```json
{
  "email": "user@example.com",
  "password": "password123"
}
```

Uses:

```js
supabase.auth.signUp()
```

Responses:

* `400` — Missing email or password
* `201` — User successfully created

### `POST /auth/login`

Uses:

```js
supabase.auth.signInWithPassword()
```

Responses:

* `400` — Empty or missing fields
* `401` — Invalid login credentials
* `200` — Successful login

Successful login returns:

* Access Token (JWT)
* Refresh Token

# 🛡️ Stage 3 — Token Verification

The protected profile endpoint was updated to verify the access token with Supabase:

```js
supabase.auth.getUser(token)
```

Invalid, expired, or modified tokens return:

```json
{
  "error": "Invalid or expired token"
}
```

Status:

```text
401 Unauthorized
```

A valid token returns the authenticated user's information:

* User ID
* Email
* Account creation date

# 🚪 Stage 4 — Middleware Protection & Logout

Token extraction and verification were moved into reusable Express middleware.

The middleware:

1. Checks the `Authorization` header.
2. Verifies the `Bearer` prefix.
3. Extracts the access token.
4. Verifies the token using Supabase.
5. Stores the authenticated user in `req.user`.
6. Stores the token in `req.token`.
7. Allows the protected route to continue.

Protected routes include:

```text
GET  /protected/profile
GET  /protected/dashboard
POST /auth/logout
```

### Logout

`POST /auth/logout` uses:

```js
supabase.auth.signOut(req.token)
```

Successful logout returns:

```text
204 No Content
```

The dashboard route was also used to verify that the reusable middleware correctly rejects invalid tokens and permits valid tokens.

## 🆚 AI vs Me

### Token Extraction

The authentication flow requires requests to use:

```http
Authorization: Bearer <token>
```

The token must be extracted after correctly handling the `Bearer` prefix.

The AI-generated implementation successfully handled authenticated requests and the protected route checkpoints.

### Invalid Tokens

Invalid or expired tokens must be rejected instead of allowing access.

The expected response is:

```text
401 Unauthorized
```

The AI-generated version successfully returned `401` for an invalid token during testing.

### What the AI Did Well

The AI-generated implementation successfully reproduced the core authentication flow and passed the required tests for:

* Public routes

* Valid authentication

# 🔒 Security Notes

Never commit the following to GitHub:

* `.env`
* Supabase credentials
* Passwords
* Access tokens
* Refresh tokens

Use `.env.example` to show the required environment variables without exposing their actual values.
